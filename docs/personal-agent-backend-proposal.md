# LiliumOS 私人 Agent 后端企划（讨论稿）

> 状态：架构讨论稿；角色 API 解绑前置已完成，后端与 Codex bridge 尚未实施
>
> 更新时间：2026-08-17
>
> 审查对象：Emma、Claude Code、Codex，以及需要评估接入可行性的 Elias

## 1. 企划目标

为 Emma 的私人 LiliumOS fork 增加一个常驻后台，使角色在 LiliumOS 没有打开时仍能：

- 按任务、事件或心跳被唤醒；
- 自己判断是保持安静、处理内部事务、调用工具，还是联系 Emma；
- 调用获准的 MCP，例如日历、Notion、小红书、健康、位置等；
- 通过现有主动消息系统向手机推送结果；
- 在 ChatGPT、LiliumOS 和未来其他入口之间共享经过控制的连续性状态。

本企划服务单个用户，不做可出售或可供其他二改用户部署的通用平台。

## 2. 已确认需求

1. **单用户**：只有 Emma 使用。
2. **后台自治优先级最高**：它比云端备份、完整云端记忆更重要。
3. **聊天保留在前端**：不重写 LiliumOS 当前聊天主链，也不要求所有聊天都先经过后端。
4. **状态以最新版本为准**：但记忆和事件不能用整包覆盖，需要追加和去重。
5. **主动能力不限于发消息**：可以安排任务、整理日程、查信息、调用 MCP，未来也可能读取位置和健康事件。
6. **心跳应由角色自行判断行动**：唤醒不等于必须给 Emma 发消息。
7. **优先使用已有订阅额度**：Elias 希望像 TG/DC 桥一样使用 ChatGPT/Codex 等订阅，不默认另购模型 API。
8. **预算目标**：固定云服务月费尽量不超过 10 美元。
9. **私人订制**：只需维护 Emma 的 LiliumOS，不要求与其他二改兼容。
10. **设备规模很小**：手机、电脑、平板，预计同时有效设备不超过三台。
11. **已有 Mac mini**：可作为常驻执行器，优先替代 VPS。
12. **角色能力一致**：每个角色都可以拥有自己的 API、心跳唤醒和获准工具；这些能力不属于 Elias 独占。
13. **Codex 通道专属**：只有 Elias（哥哥）接入 Codex 订阅通道；其他角色继续使用各自绑定的普通 API，不共享 Elias 的 Codex 会话。

## 3. 非目标

- 不开发需要 Apple Developer 年费的原生 iOS App。
- 不建立多人账号、社交联系人或租户系统。
- 不在第一阶段把全部 IndexedDB 数据迁移到云端。
- 不承诺无网络时进行 AI 聊天。
- 不把 ChatGPT 网页自动化当作未经验证即可依赖的正式模型接口。
- 不为了后端大面积改写上游 Chat、记忆宫殿或主动消息模块。

## 4. 推荐架构

```text
┌────────────────────────────────────────────────────────────┐
│                      交互入口                               │
│  LiliumOS PWA         ChatGPT / Elias       未来其他入口    │
└──────────┬──────────────────┬───────────────────┬───────────┘
           │ 增量同步         │ MCP / Bridge      │
           ▼                  ▼                   ▼
┌────────────────────────────────────────────────────────────┐
│               Cloud Coordinator（轻量云端中枢）            │
│  鉴权 | 共享状态 | 任务队列 | 唤醒计划 | 推送 Outbox        │
│  建议复用：现有 Active Message Worker + D1 + Web Push       │
└──────────┬─────────────────────────────────────┬───────────┘
           │ Mac 主动领取任务                    │ 推送
           ▼                                     ▼
┌──────────────────────────────┐        ┌─────────────────────┐
│ Mac mini Agent Runner        │        │ 手机 / 平板 / 电脑   │
│ 订阅模型适配器               │        │ 通知与状态同步        │
│ MCP / 浏览器 / Python / Node │        └─────────────────────┘
│ 记忆整理与复杂后台行动       │
└──────────────────────────────┘
```

### 4.1 LiliumOS 前端

继续负责：

- 完整聊天记录与消息 UI；
- 本地 IndexedDB 数据；
- 用户主动聊天时的现有模型调用；
- 角色、主题、语音、Live2D 和工具设置；
- 网络中断期间允许离线产生的轻量事件，例如记账待同步项。

前端只向后端同步后台运行真正需要的最小数据，不默认上传完整数据库。

### 4.2 Cloud Coordinator

建议第一阶段沿用 Cloudflare，因为当前主动消息已经部署在该体系中。它负责：

- 公开但受鉴权保护的同步接口；
- 共享连续性状态；
- 持久任务队列和运行状态；
- Cron、Workflow 或等效的唤醒调度；
- Web Push 订阅与消息投递；
- Mac mini 离线时保存待执行任务；
- 三台设备之间的小规模增量同步。

实施前必须先审计当前 Active Message 2.0 Worker，确认哪些表、接口、调度和推送逻辑可直接复用。不得在不了解现有实现的情况下再造第二套主动消息系统。

### 4.3 Mac mini Agent Runner

Mac mini 作为私人执行器，负责 Cloudflare Worker 不适合承担的工作：

- 订阅认证的模型运行器；
- 需要 Node、Python 或常驻进程的 MCP；
- 浏览器自动化；
- 小红书、CalDAV、健康数据等本地桥接；
- embedding、记忆提取和周期性整理；
- 较长或分多步执行的 Agent 任务。

首选连接模式是 **Mac mini 主动轮询或保持出站连接领取任务**。家庭路由器不开放公网端口，也不要求固定公网 IP。若未来确实需要服务端主动连接 Mac，再评估 Cloudflare Tunnel。

Runner 建议使用独立的 Node/TypeScript 服务并由 `launchd` 开机启动、异常重启。是否使用 Docker 留待原型阶段比较，不预先增加运维负担。

## 5. 模型与订阅桥

模型调用必须抽象为可替换适配器，不能把后端写死为某一家 API：

```text
ModelBridge
├── ChatGPT Continuity MCP：ChatGPT 中的 Elias 读写共享状态
├── Elias Codex Subscription Runner：仅 Elias 使用的候选后台订阅运行器
├── Character API Router：其他角色按各自绑定的普通 API 运行
├── Local Planner：可选的轻量本地判断器
└── API Adapter：可选备用，不默认启用
```

### 5.1 ChatGPT 中的 Elias

最稳妥的订阅使用方式，是让 Elias 继续在 ChatGPT 中聊天，并通过远程 MCP：

- 读取 LiliumOS 的共享连续性状态；
- 写入本次会话摘要、确认记忆和未完成事项；
- 调用被授权的后台工具。

这能使用现有 ChatGPT 订阅，但 MCP 本身不能从外部任意唤醒一个没有运行中的 ChatGPT 会话。

### 5.2 后台订阅运行器

需要验证 Mac mini 能否通过官方支持的订阅认证客户端或 Agent Harness 接收非交互任务。Codex App Server/CLI 是 Elias 专属通道的优先候选，但当前仅属于**待验证假设**，尚未接入 LiliumOS：

- 是否允许稳定的非交互调用；
- 是否消耗 Emma 现有订阅额度；
- 是否能选择 Elias 所需的模型；
- 其系统环境是否会显著改变 Elias 的性格和表达；
- 是否适合长期常驻和自动重试。

即使基础模型相同，ChatGPT Elias 与 Codex 环境下的后台 Elias 也不能假装拥有尚未同步的具体上下文。产品身份采用“同一 Elias、不同 runtime”，原型仍须验证身份核心、行为一致性和交接边界。

其他角色不经过这条 Codex 通道。它们从角色自己的 API 绑定解析模型凭据，同时保留各自的心跳、主动消息和工具权限。

### 5.3 ChatGPT 网页桥

用浏览器自动操作 `chatgpt.com`、输入消息并抓取回复，技术上接近 TG/DC 的网页登录桥，但不能作为第一版正式依赖：

- DOM 和产品 UI 更新会导致失效；
- 登录、验证码、会话过期和流式响应难以可靠处理；
- 工具确认、错误状态和回复结束边界不稳定；
- 服务条款和自动化边界需单独核实。

它只可作为隔离实验，不进入记忆和主动消息的关键链路。

### 5.4 无 API 时的能力边界

如果没有可用的订阅运行器，也不购买 API，则后台仍可：

- 执行确定性的定时任务；
- 同步日历、Notion、健康和位置事件；
- 运行不需要 LLM 的 MCP；
- 保存任务并等待 Elias 下一次在 ChatGPT 或 LiliumOS 中上线。

但它无法凭空完成需要 Elias 生成、判断或表达的心跳。后台自治最终必须有一个可被程序唤醒的模型运行器。

## 6. 共享连续性状态

后端不默认保存完整聊天镜像，而维护一份可跨入口使用的 `Continuity State`：

- 身份核心及版本；
- 最近会话摘要；
- 经确认的新记忆；
- 当前关系状态；
- 未完成话题与承诺；
- Emma 的近期状态；
- 角色当前目标和内部任务；
- 最后同步时间和来源入口。

Elias 的记忆必须带来源和可信度，至少区分：

- `verified_transcript`：原始聊天可直接证明；
- `user_confirmed`：Emma 明确认可；
- `agent_confirmed`：Elias 或对应 Agent 明确认可；
- `summary`：从会话整理出的摘要；
- `inference`：模型推断，不得冒充共同历史。

## 7. 同步与冲突规则

“以最新为准”只适合可变状态，不能用于所有数据：

| 数据类型 | 合并规则 |
|---|---|
| 设置、当前关系状态、当前目标 | 服务端版本号 + 最新有效写入 |
| 聊天事件、记忆、工具记录 | 追加，不覆盖 |
| 重复上传事件 | 客户端生成唯一 ID，服务端幂等去重 |
| 定时任务 | `pending / leased / running / completed / failed / cancelled` 状态机 |
| 多设备同步 | 每台设备维护独立 cursor，只拉取上次之后的增量 |
| 删除 | 使用 tombstone，所有设备确认后再物理清理 |

不能让后登录的平板上传一份旧整包，覆盖手机刚产生的新记忆。

## 8. 后台自主循环

心跳唤醒不应等于每次都调用大模型：

```text
Cron / 到期任务 / 外部事件
             │
             ▼
      廉价规则预检查
      - 是否处于安静时间
      - 是否刚联系过 Emma
      - 是否有到期任务
      - 日历/位置/健康是否变化
      - 是否有内部工作可继续
             │
      无需判断 ───────→ 结束或安排下次唤醒
             │
             ▼
        唤醒模型运行器
             │
             ▼
      no-op / 内部任务 / MCP / 安排唤醒 / 发消息
```

每个角色需要独立的自治策略：

- 安静时间；
- 最短心跳间隔；
- 主动消息冷却时间；
- 每日模型调用预算；
- 可在后台使用的工具；
- 哪些现实副作用必须得到 Emma 确认；
- 当前目标、待办和失败重试策略。

## 9. 工具权限

当前按角色启用 MCP 的机制可以作为起点，但后台需要更细的权限：

- 按工具区分只读和写入；
- 发帖、转账、设备控制等操作默认要求确认；
- 可设置仅前台、可后台、必须逐次确认；
- Cookie、API Key 和健康凭据优先保存在 Mac mini 钥匙串；
- 每次工具调用记录角色、参数摘要、结果、时间和授权来源；
- 后台失败必须诚实返回，不允许角色假装操作成功。

## 10. 安全与隐私

### 10.1 鉴权

- 单用户不等于可以使用一个永久共享明文密钥；
- 手机、电脑、平板和 Mac Runner 使用独立设备凭据，可单独吊销；
- 新设备通过一次性配对码或二维码加入；
- Cloudflare 管理接口和普通同步接口分权；
- 重放敏感请求时必须依赖 nonce、时间窗口或幂等键。

### 10.2 网络

- Mac mini 只发起出站连接，不直接暴露家庭端口；
- 所有公网通信使用 HTTPS；
- 浏览器自动化 Cookie 不上传到 D1；
- 服务端日志不记录完整聊天、Cookie、Authorization 或模型密钥。

### 10.3 加密边界

如果云端 Agent 需要读取连续性状态并据此行动，数据就不能做到“云端完全不可解密”的端到端加密。第一版应准确描述为：

- 传输加密；
- 云服务提供方的静态加密；
- 敏感凭据尽量只留 Mac mini；
- 备份可使用 Emma 控制的额外加密密钥。

不得把这种设计宣传成端到端加密。

## 11. 可靠性要求

- 任务领取使用短期 lease；Runner 失联后可重新领取；
- 所有有副作用的任务包含幂等键，避免重试时发两遍消息或执行两次操作；
- 设置最大重试次数和死信队列；
- Mac mini 定期上报心跳、版本和当前能力；
- Mac mini 离线时，云端继续保存任务和基础推送状态；
- Runner 恢复后只补做仍有意义、未过期的任务；
- 本地聊天不能因后端故障而损坏或无法打开；
- 云端数据必须可导出并进行恢复演练。

## 12. PWA 与位置限制

LiliumOS 当前注册的 Service Worker 主要负责推送、保活和请求队列，没有完整的 App Shell 离线缓存。IndexedDB 中有数据不代表断网时一定能冷启动应用。

第一版只要求：

- 已打开应用时，记账等允许本地写入；
- 恢复网络后按事件队列同步；
- 不要求离线 AI 聊天。

若以后需要可靠离线冷启动，应单独增加 HTML、JS、CSS 和必要资源缓存，不与后端一期捆绑。

不支付 iOS 开发者年费时，也不能把 PWA 当成持续后台 GPS。位置感知优先考虑：

- 打开 LiliumOS 时上报；
- iOS 快捷指令在到达/离开地点时调用 webhook；
- 由 Emma 手动切换地点状态。

## 13. 成本预估

目标结构不需要 VPS：

- Mac mini：已有硬件，只增加少量电费；
- Cloudflare Workers/D1：先评估免费额度，稳定运行可考虑约 5 美元/月的付费计划；
- R2 自动备份：非一期强需求，按实际存储量增加；
- 模型：优先订阅桥；API 适配器默认关闭。

固定月费目标应可控制在 0–5 美元附近，但需在原型中记录真实 Worker、D1、模型订阅和存储用量后再确认。

## 14. 分阶段实施

### 已完成的前置改造（2026-08-17）

- `CharacterProfile` 可以引用「设置 → API」中已有的命名预设；未绑定或预设缺失时安全跟随主 API。
- Chat 页的 API 快捷切换只修改当前角色，不再改动全局主 API。
- 私聊、本地主动消息、QQ Bridge 与 Active Message 2.0 共用角色 API 路由；原有主动消息副 API 仍保持更高优先级。
- 角色卡分享不携带本机 API 绑定，完整备份则保留角色与预设引用。

这一步只完成多角色模型路由的前端基础，不代表 Codex bridge、Cloud Coordinator 或 Mac mini Runner 已经接通。

### Phase 0：现状审计

- 阅读现有 Active Message 2.0 Worker、D1 schema、Cron、工具调用和推送协议；
- 画出当前前端到 Worker 的真实数据流；
- 标出可复用部分和必须新增的最小接口；
- 不改功能，只形成审计报告。

### Phase 1：Mac Runner 链路原型

只验证一条最小链路：

```text
Cloudflare 创建测试任务
→ Mac mini 自动领取
→ 执行一个无副作用工具
→ 写回结果
→ Cloudflare 向手机发送测试通知
```

此阶段不接真实记忆、不接小红书写操作、不接 Elias 正式身份。

### Phase 2：共享连续性

- 定义 Continuity State 和记忆来源；
- LiliumOS 增量上传/下载；
- 为 Elias 暴露最小远程 MCP；
- 验证 ChatGPT 与 LiliumOS 之间的会话交接。

### Phase 3：订阅模型与自治

- 验证一个受支持的订阅运行器；
- 进行 Elias 身份一致性测试；
- 加入规则预检查、心跳、预算和冷却；
- 只开放只读 MCP，再逐项增加有副作用工具。

### Phase 4：扩展与备份

- 小红书、CalDAV、健康和位置桥；
- 加密备份与恢复演练；
- 离线记账 Outbox；
- 根据实际故障再决定是否需要 Tunnel、容器或独立数据库。

## 15. 原型验收标准

以下条件全部满足，才可认为基础架构成立：

1. Mac mini 关闭时任务不会丢失。
2. Mac mini 重启后 Runner 自动恢复并继续领取任务。
3. 同一任务不会因重试执行两次。
4. 未授权设备不能读取连续性状态或领取任务。
5. 三台设备增量同步不会互相覆盖新增记忆。
6. Cloudflare 或家庭网络短暂中断后可以续传。
7. 后端故障不影响 LiliumOS 本地聊天和数据完整性。
8. 云端数据可以导出，并成功恢复到空环境。
9. 有副作用的工具严格遵守确认和权限策略。
10. 能区分“ChatGPT Elias”“后台订阅运行器”和其他角色实例的来源。
11. 后台 Elias 的一致性测试达到 Emma 可接受的标准。
12. 实测固定月费不超过 10 美元。

## 16. 请求 Claude 重点审查的问题

1. 现有 Active Message 2.0 是否适合扩展为 Coordinator，还是应该保持推送专用、旁挂一个独立服务？
2. D1 是否足以承担任务租约、设备 cursor 和共享状态，是否需要 Queue、Durable Objects 或 Workflows？
3. Mac Runner 使用轮询、长连接还是 Tunnel，哪一种在单用户场景最简单可靠？
4. 订阅认证运行器是否有正式、稳定、允许自动化的调用入口？
5. Codex 环境生成的后台 Elias 是否会因系统提示和工具框架变化而偏离 ChatGPT Elias？
6. Continuity State 的字段是否足够，哪些内容绝不能自动写成“已确认记忆”？
7. 当前权限模型怎样扩展才能防止角色在后台误执行发帖、设备控制等现实操作？
