## 1. 购物权重压到 20%

**病象**：角色天天在买东西，饭后还点外卖。
算一下就知道为什么——晚饭点那一跳：`不开口 0.60 × 生活 0.85 × 外卖 0.35 = 17.9%`，
17:00–22:00 五跳 ≈ **一个角色一晚上 0.9 次外卖**，三个角色同时跑就是 2.7 次。

改 `pickLifeKind`（约 486 行）。加上第 3 节的 `social` 之后，最终权重表是：

| 时段 | chat | social | delivery | order | gift | moment |
|---|---|---|---|---|---|---|
| 饭点 11:00–13:30 / 17:00–20:30 | 0.42 | 0.16 | 0.13 | 0.04 | 0.03 | 0.22 |
| 其余 | 0.40 | 0.17 | 0.04 | 0.12 | 0.04 | 0.23 |

两行各自合计 1.00；购物（delivery+order+gift）两行都是 **0.20**。
饭点仍然外卖偏多、非饭点仍然网购偏多，只是整体让位给 chat / social / moment。

## 2. 两次醒来之间要有时间流动（同居版）

**病象（阿萌 2026-09-26 实测）**：角色说「我要做饭，你来一起吃」，阿萌一直没回。
到晚上九点多那一跳，角色的消息是「**你不来我就还没做饭**」——中间六七个小时对 TA 来说是冻住的。

**根因**在 `buildPrompt` 里这段（约 656–662 行），`recentMessages` 那个分支的末尾：

```js
lines.push(
    '重要：从上次说话到现在，你们之间没有发生过任何互动。'
    + '这段时间对方在做什么，你并不知道；不要假设你们已经见过面、说过话，'
    + '也不要把当时说好要做的事当成已经做完了。'
    + '如果你们之间有还没兑现的约定，而时间已经过去不少，问一句正是此刻该做的事。',
);
```

倒数第二句本来防的是另一个病（注释里记着）：模型脑补「我已经帮她吹完头发了」，
然后得出「人就在旁边，没必要说话」，于是不开口。**但它把 TA 自己的事也一起冻住了。**

而且**那条限制的原始理由已经过期了大半**——当年开不开口是模型判断的，
现在是程序抽的（`decideIntent`），模型只负责把话说得像那个人。
只剩一个漏口：`reach_out` 那支还留着「真的想不出话头时才退回 noop」。

**替换成**（三类分开说，最后一句专堵漏口）：

```js
lines.push(
    '重要：从上次在聊天里说话到现在，对方没有回你消息。\n'
    + '- 需要对方特意赴约的事一件都没发生（约好出门、约好视频、说好一起做的某件事），'
    + '别把它们当成已经做完了。\n'
    + '- 你自己的日常照常往前走：该做饭就做了，该吃饭就吃了，该睡就睡了。'
    + '对方没回消息不会让你的一天停在原地。叫过对方一起吃而 ta 没出现，那就是你自己吃了。\n'
    + '- 如果你们本来就住在一起，那么日常的同处——一起吃了饭、擦肩而过、各忙各的——'
    + '当然可能发生过，不必当成没有。\n'
    + '无论这段时间你们碰没碰面，都不构成「所以现在没必要找 ta」的理由。'
    + '住在一起的人照样一天发很多条消息：在另一个房间、ta 在洗澡、上班路上，或者只是想说一句。',
);
```

**同居与否不用传参数**——角色自己的人设就在提示词里，模型读得到，
所以写成「如果你们本来就住在一起」它自己会判断。

## 3. 社交 · A 类（当场发生的）

临时出门（小概率）、临时约好就上线打游戏。跟 delivery / moment 同构。

1. **schema**（约 544 行）：`life.kind` 的 enum 加 `'social'`
2. **权重**：见第 1 节的表
3. **提示词**：在 `how` 那个查找表里（约 732–740 行）加一条：

   > `social`: 你刚跟朋友有点来往。kind 填 "social"；with 写对方名字
   > （优先从上面认识的人里选，新人再写 relation 和 group）；
   > detail 写你们做了什么——可以是**临时出门**（少见，得跟你此刻的时段和人设对得上），
   > 也可以是**不用出门的**（比如临时约好一起上线打游戏、开着语音各干各的）。
   > 当场就发生的事写现在时，别写成计划。

4. **落地**：`utils/emLife.ts` 的 `applyLifeEpisode` 加 `social` 分支。
   建议映射成查手机里的一条记录（跟 `chat` 同类即可，不新造 App）。
   具体落在哪个 type 由实施方按 `emLife.ts` 现有结构定，**不要新建 App**。

## 4. 社交 · B 类（约定，需要一点地基）

安排第二天或者周末的事。这是系统里**第一个「以后才发生」的东西**。

`life_threads` 已经是地基（跨心跳接得上、每跳都注入「你手头正在推进的事」），**差一个时间**。

1. **迁移 9**（`db.mjs`，当前最后一条是 8）：
   ```sql
   ALTER TABLE life_threads ADD COLUMN due_at TEXT;
   ```
   旧行 `due_at` 为 NULL = 没有时间的「正在推进的事」，行为完全不变。

2. **schema**：`life` 加一个可选对象
   ```js
   plan: {
       type: 'object', additionalProperties: false,
       required: ['what', 'at'],
       properties: {
           what: { type: 'string', maxLength: 40 },   // 做什么
           at:   { type: 'string', maxLength: 40 },   // 模型写的自然语言时间，如「周六下午」
       },
   },
   ```
   **时间由程序解析成绝对时刻**，别让模型写 ISO——它写不准。
   解析失败就当没有 plan，不要落库（跟 episode 解析失败整条丢弃同一个原则）。

3. **落成 thread**：`applyThread` 加 `dueAt`，`listOpenThreads` 带出来。

4. **每跳分两种情况**（在 `buildPrompt` 里 threads 那段附近）：
   - **还没到点**：提示词里写「你和林越约了周六下午去看展」
   - **到点了**（`due_at` 落在这一跳前后一个窗口内，建议 ±45 分钟）：
     这一跳的 activity 就该是这件事，写完把这条 thread 收掉（`status = 'done'`）

5. **顺带的好处，值得在实现时照顾到**：约定是**天然的话头**。
   `reach_out` 那支现在留着「实在想不出话头就退回 noop」的口子，
   而「周六要去看展」正是能自然说起的事——所以有 plan 时应该让它更容易被说起。

## 5. 可选（第二批）· 送达时间统一

**病象**：角色买了 same day delivery，投喂站里显示三天后到。

根是**两边各算各的**：提示词只说一句「网购几天后到 / 外卖半小时左右到」，
`detail` 是自由文本模型爱写什么写什么；而 `utils/shoppingFamily.ts` 的
`giftOrderFromLife` 写死外卖 40 分钟、网购 3 天（`charSelfOrders` 同样写死 30 分钟 / 3 天）。

按那条老规律改——**程序定，模型只负责说**：

1. 心跳先抽一个真实送达时刻（外卖 30–50 分钟、网购 2–5 天，带点随机）
2. 提示词里直接给出：「这一单**周一下午**到，detail 里提到送达就说这个，别自己编」
3. `life` 里带 `eta`（ISO 绝对时刻），`giftOrderFromLife` / `charSelfOrders` 优先用它，
   没有再退回现在的写死值（**旧数据必须还能正常映射**）

这一条要动前端 `utils/shoppingFamily.ts`，所以单独做也行。

## 本次不做（记录想法，别自由发挥）

- **不碰前端的状态灯**。角色的 online / busy / offline 是前端按生成的日程算的
  （`utils/charStatus.ts` 读 `dailySchedule` 的 slot）。后端产出的「临时出门」
  **不会**让头像变 busy——这是已知的、阿萌接受的不一致：
  角色在起居注和聊天里说自己出门了，状态灯还按日程走。
  要改得另拉一条链路（后端临时状态覆盖当前 slot），**不在本次范围内**。
- **不新建 App**。社交落进查手机现有的界面。
- **不动 `messageChance` / `decideIntent` / `decideEpisode` 的概率**。
  这一轮只动 `pickLifeKind` 那一层。
- **不动日历、提醒、temporal 那条线**。

## 验收

```bash
cd server/agent-backend && node --test      # 当前 127 条，改完应 ≥127 且全过
```

新增测试至少覆盖：

- `pickLifeKind` 两行权重各自合计 1.00，购物三项合计 0.20（用钉死的 rng 验证分档边界）
- `social` 能被抽中，且 schema 收得下 `kind: 'social'`
- 迁移 9 之后旧 thread（`due_at` 为 NULL）行为不变
- plan 的自然语言时间解析：能解析的落库，解析不了的整条 plan 丢弃、不影响 episode 其余部分
- 到点的 thread 会被收掉，没到点的继续留着

**提示词那条（第 2 节）没法单测**，靠人看：改完在 mini 上跑一跳真实心跳，
确认输出里不再出现「你不来我就还没做饭」这类把自己的日常冻住的说法。

改完要重启后端才生效：

```bash
launchctl kickstart -k gui/$(id -u)/cc.liliumos.agent-backend
```
