# 花销分析：手动排除与金额分位数

日期：2026-09-16。状态：开发分支 `codex/finance-spending-scope` 已实现，待 Emma 体验；未发布正式站。本文记录方案对比、选型、最终行为及验收，不替代用户验收。

## 要解决的问题

账本需要保存全部真实资金流，但看生活花销时，需要把替别人代充、偶发家具等支出单独拿出来。代充是对方先付款，不需要做应收款追账。收入与付款都保留在账本，分别手动标记为代收代付。之前 SimpleFIN 的 Instacart hold 修复是来源纠错，与此次分析筛选不同，不能共用隐藏流水的字段。

## GitHub 调研与四种方案

| 方案 | 做法 | 好处 | 代价与限制 | 本次决定 |
| --- | --- | --- | --- | --- |
| A：分类/标签筛选 | 把代充、家具放进分类或标签，在报表里排除 | 规则直观；适合反复使用的报表 | 分类承担“买了什么”和“是否代表日常”两种职责；无法灵活处理同分类里的个别交易；不能自动观察大额影响 | 借鉴报表过滤，不用改分类树 |
| B：手动标记 + percentile | 每笔独立标记，再按当前范围的单笔金额计算分位数；三种总额对照 | 同时处理代付语义和金额大额；可恢复、可解释；符合用户选择 | 分位数只表示相对大小，不证明交易异常；小样本会敏感 | **采用** |
| C：IQR / MAD / 自动异常检测 | 用箱线图、稳健离差或模型识别异常金额 | 在大量数据中可减少人工操作 | 日常消费天然偏斜；房租会成为异常，调参解释成本高；不能识别小额代付；没有用户确认的标注数据 | 不用于第一版 |
| D：报销/清算账本 + 消费摊销 | 关联收款、付款、欠款状态；把家具按月摊销 | 能做专业代收代付核对、跨期分摊 | 先收款的代充并不需要追债；摊销会引入新的虚拟金额与会计口径 | 留作将来独立需求 |

查阅依据（2026-09-16）：

- [Actual Budget custom reports](https://actualbudget.org/docs/reports/custom-reports/) 支持报表过滤与保存；[tags](https://actualbudget.org/docs/transactions/tags/) 与 [split transactions](https://actualbudget.org/docs/transactions/split-transactions/) 提供更细粒度组织。GitHub 源码在 `actualbudget/actual` 提交 `5f60f2971ca0f4a84133ba43a047a9f7b029d409`：`packages/desktop-client/src/components/reports/reports/CustomReport.tsx` 使用 `isNot/notOneOf` 条件，`spreadsheets/custom-spreadsheet.ts` 在聚合前构造过滤条件。本次借鉴“保存的报表口径”，不复制其框架。
- [Sure issue #1994](https://github.com/we-promise/sure/issues/1994) 讨论 excluded 与 one-time 不应混为一谈；[PR #1995](https://github.com/we-promise/sure/pull/1995) 在检索时仍 open、未合并，不能当作已上线行为。检阅 main 提交 `8ea2026271acca5542a21866cdd89793f0190243` 的 `app/models/transaction.rb` 和 `app/models/income_statement/totals.rb`，其预算排除类型包含 `one_time`。本次因此明确保留完整支出比较，避免一次性消费从历史里消失。
- [Firefly III collector interface](https://github.com/firefly-iii/firefly-iii/blob/6143c0f14f490ee374f5aac344a9491ba162a8c1/app/Helpers/Collector/GroupCollectorInterface.php) 提供分类、账户、预算排除；[讨论 #8724](https://github.com/orgs/firefly-iii/discussions/8724) 涉及过手资金。本次复用“数据仍在、报表改变范围”的思路。
- [R quantile 官方说明](https://stat.ethz.ch/R-manual/R-devel/library/stats/html/quantile.html) 的 type 7 为本次分位数插值定义。不是引入 R 依赖，前端自行实现相同公式。

选择 B 是基于上述设计模式和用户明确偏好作出的本项目决定；没有发现一个可直接接入现有 LiliumOS、同时完整满足本次语义的现成模块。无需增加依赖或把私人账本送到外部异常检测服务。

## 最终产品行为

入口：记账 → 分析 → 花销口径。保留原有周/月/年、账户、币种筛选。

始终显示三组已入账支出及笔数：

1. **全部支出**：包含手动排除项，作为原始比较。
2. **手动排除后**：移除代收代付、一次性支出、其他排除项。
3. **再排大额后**：在第 2 组基础上，去掉高于所选分位数阈值的支出，“始终保留”例外。

默认选“手动排除后”，分位数默认 P95。不会默认自动认定家具或任何真实交易应被排除。用户选中的口径与分位数保存在本机，刷新可恢复。

交易支持：正常计入、始终保留、代收代付、一次性支出、其他排除。恢复“正常计入”可撤销手动决定。“始终保留”适合房租等需要纳入日常观察的大额。分析页明细可搜索、仅看被排除项；单笔编辑页也能修改，流水列表显示标记。

代充的到账与付款各标记一次，两笔都不从原始流水移除。收入不参与金额分位数；在排除视图中手动标记的收入也不计入。第一版不自动配对预收款、不推断债权、不识别手续费利润；若某一笔混合自己的消费与代付，目前需要先有分开的真实记录，不支持此次新建部分金额排除。

## 算法与边界

先限定日期、账户、币种，再排除转账、信用卡还款类记录、已纠错的来源 hold、待入账、非正数/非有限金额。完整比较也只表示有效已入账消费，不是把银行卡每一行都相加。货币不换算、不混算；用户选择不同周期会产生不同阈值。

对手动排除后的 n 笔支出金额排序，位置为 `(n - 1) × percentile / 100`，在相邻位置线性插值。只移除严格大于阈值的金额，相等值保留；不为了凑足 5% 强行拆开同额交易。P100 不排大额，单笔样本不会被排除，空样本显示暂无阈值。百分位输入范围 50–100，支持小数。界面金额四舍五入显示并标“约”，判断使用原始插值精度。

“始终保留”的交易参与原始样本计算，但豁免移除；所以实际移除数量可能少于名义比例。只计算一次，不在删除最大交易后反复计算。少于 20 笔显示提醒；20 是产品提示门槛，不是统计可靠性的保证。所谓大额候选只意味着在当前样本中金额靠上，不证明不合理、欺诈、错误或可节省。

退款沿用旧系统的收入展示，暂不净抵原消费；需要净消费分析时再另做跨期退款关联。预算进度、分类图表和当前总额跟随选中口径，并显示“按当前口径”；余额和原始流水不随口径变动。差额不能说成省下的钱。

## 数据与集成

- 新增可选 `FinanceTransaction.analysisTreatment`。旧数据无字段视为正常计入，不需要 IndexedDB 版本迁移。
- 分位数结果只在读取时计算，不落成永久删除/隐藏字段，不复用 `excludedFromReporting`。
- 明细修改采用只更新标记的原子写入，避免拿旧界面副本覆盖最新金额。SimpleFIN 写入时保留当前本机标记，包括恢复正常；pending 到正式扣款的已有匹配路径也保留标记。
- Finance 完整导出/导入保存交易字段与设置。代码通过 Git 跨电脑同步不等于浏览器账本自动同步；标记跟随现有备份/恢复渠道，不写回银行。
- 公共计算函数供页面与 `finance_get_spending_summary` 共用。聊天汇总使用保存的口径和百分位，返回三组比较与样本信息；默认所有账户，明确 `account_scope: all`，按所查日期/各币种计算，因此不保证与页面临时选中某账户时金额相同。
- 最近交易/搜索仍返回原始流水，同时注明手动标记。新增账目感知只累计未手动排除的已入账支出，不从几条新流水单独计算百分位；提示角色用正式汇总查询生活花销。
- “TA 怎么看”只分析当前口径支出，缓存随范围、标记与交易内容变化失效，防止切换后显示旧口径回复；没有调用真实模型测试文风质量。

```sh
node node_modules/vite/bin/vite.js --host 127.0.0.1 --port 5183 --strictPort
```
